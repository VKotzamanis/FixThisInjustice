# Design Mode: editing the real app, and getting the edits back

> **For agentic workers:** REQUIRED READING before any task here:
> `docs/plans/subagent-briefs/00-CONTEXT.md`. Steps use `- [ ]`.

**Goal:** let the owner do graphic design on the onboarding — colours, fonts, copy, assets,
placement — **in the running app**, and get every edit back into the repository as a reviewable
patch rather than as a description of what he wants.

**Architecture:** a `?design=1` mode inside the real app, hard-gated out of production builds. It
makes copy strings editable in place, exposes every token as a live control per skin, accepts
dropped images into placeholder frames, and collects layout notes as pins. One button exports a
structured patch; one script applies it back to `copy.ts`, `tokens.css` and `public/`.

**Tech stack:** React 19, TypeScript, Vite, Zustand, vitest. No new runtime dependency.

---

## Why not a separate editable page

<!-- decision: design-mode-in-the-real-app | status: adopted | supersedes: design-mode-mirror-page -->

The obvious build is a standalone HTML mirror of the onboarding with `contenteditable` on the
text. It is a weekend's work and it is the wrong thing, for a reason this project has now
demonstrated seven times in one round: **it is a value transcribed into a second place.** The
mirror is stale the moment either side changes, and design decisions would be made against a page
that no longer matches what ships.

It also shows ONE skin. Three ship, and the two worst defects found in round 2 were contrast
failures visible only on limelight: the REFERENCES control at 1.41:1 and the feasibility pastels
at 1.04:1 against the lime ground. A mirror hides exactly the class of bug this tool exists to
catch.

### The established tools, and why none of them is adopted

- **TinaCMS** does git-backed visual in-place editing and is the closest thing to this design.
  Rejected because it is a *CMS*: content lives in files it owns, modelled its way. This app's copy
  is a TypeScript union pinned byte-for-byte by `catalogue.json`, with a per-skin override layer and
  a fourteen-rule contract enforced by four scripts and CI. Migrating to Tina's content model means
  discarding the guardrails, and those guardrails caught three real defects in the last round.
- **Puck** is MIT and drag-and-drop for React. Rejected because it composes pages from blocks, and
  the onboarding is a wizard with validation gates and derived state, not a block layout.
- **Plasmic** is hosted. Rejected because it puts the copy of an app making health claims on a third
  party's server.

What is kept from them is Tina's central idea — contextual editing on the live page — without the
CMS underneath it.

## What round-trips, and what does not

<!-- decision: layout-is-annotated-not-edited | status: adopted | supersedes: none -->

| Editable | Lives in | Round-trips? |
| --- | --- | --- |
| Copy text | `copy.ts`, every string already has a unique key | **Yes** |
| Colours | `tokens.css`, 121 declarations, per skin | **Yes** |
| Font family | `--sans` / `--mono` tokens | **Yes** |
| Font size, weight, scale | **nothing — not tokenised today** | **After Task 0** |
| Images | `ArtworkPlaceholder` frames naming register rows | **Yes** |
| **Layout, box position** | React structure plus CSS | **NO** |

**Layout is the trap and it is deliberately out of scope for editing.** A WYSIWYG that lets a box
be dragged produces absolute positions that do not map back onto component structure; the result
is a pile of coordinates someone then has to reinterpret, which is worse than a sentence. So
layout is **annotated**: click a thing, leave a note, and it arrives as `[part-id] note` for a
human to implement.

This is the honest line between what the machine can carry and what it cannot. Do not move it
without saying why.

## Task 0: tokenise the type scale (prerequisite for fonts only)

**Skip this if the first pass is colours and copy.** It blocks nothing else.

`tokens.css` has 121 declarations and **not one of them is a font size, weight or line height** —
only `--sans` and `--mono` for families. "Edit the font type and style" is not reachable until the
scale is tokens.

- [ ] Add a type scale to the bare `:root` block: sizes, weights, line heights, letter spacing.
- [ ] Replace the hard-coded values in the setup and intro stylesheets with those tokens. **Only
      those two areas.** A repository-wide sweep is a separate job and is not this one.
- [ ] `src/skins/tokens.test.ts` asserts the `:root` token count. It will need updating; its own
      comment shows that count being bumped deliberately each time, so follow the pattern.

## Task 1: the gate, the panel, and the colour loop, end to end

**This is the task that makes the tool usable. Everything after it is an extension.**

**Files:** `src/design/` (new), `src/app/App.tsx`, `vite.config.ts`, `.github/workflows/ci.yml`,
`scripts/design-patch.mjs` (new)

### 1a. The gate

- [ ] Design Mode activates on `?design=1` AND only when `import.meta.env.DEV` or an explicit
      `VITE_DESIGN_MODE` flag is set. It must be impossible to reach in the deployed app.
- [ ] Dead-strip it from production: the whole module tree behind one `if (!DESIGN_MODE) return null`
      that Vite can eliminate.
- [ ] **A CI step greps the built bundle for a design-mode marker string and fails if it is
      present.** Model it on the personal-data grep already in `ci.yml`, which exists for exactly
      this shape of risk. A gate that is not asserted is a gate that regresses.

### 1b. The token panel

- [ ] Enumerate every token by parsing `tokens.css`. **`src/skins/tokens.test.ts` already does
      this** with `tokensIn(":root[data-skin='limelight']")` — reuse that approach rather than
      writing a second parser.
- [ ] Render one control per token, grouped: colour tokens get a colour input, everything else a
      text input. Writing a control sets the custom property on `document.documentElement` live.
- [ ] **A skin switcher at the top of the panel.** The app already mirrors the skin onto
      `<html data-skin>` (`App.tsx:603`), so flipping it re-renders in that skin's tokens. This is
      the single most important control in the tool: it is what makes a 1.41:1 mistake visible
      before it ships instead of after.
- [ ] Show a live contrast ratio beside any token pair the panel can identify as text-on-ground,
      with the WCAG thresholds named: 4.5:1 for body text, 3:1 for anything else you must see.
- [ ] Edits persist to `localStorage` so a reload does not lose an afternoon.

### 1c. Export and apply

- [ ] One **Export** button producing JSON:
      `{ version, generatedAt, tokens: { <skin>: { <token>: <value> } }, copy: {}, assets: [], notes: [] }`
- [ ] `scripts/design-patch.mjs <patch.json>` applies it: token edits rewrite the matching
      declarations in `tokens.css`, in place, preserving comments and order.
- [ ] **The applier NEVER writes silently.** It prints a diff and requires `--write`. A tool that
      edits the source of a health-claims app on a single argument is a tool that will one day eat
      something.
- [ ] It refuses a patch whose `version` it does not know.

## Task 2: in-place copy editing

**Files:** `src/content/copy.ts` (the accessor only), `src/design/`, `scripts/design-patch.mjs`

- [ ] Every rendered string already passes through `copy(key)` / `copyFor(skin, key)`. In design
      mode, wrap the return in a span carrying `data-copy-key`, and make those `contenteditable`.
- [ ] **Take `textContent` only, never `innerHTML`.** `contenteditable` produces markup the moment
      anything is pasted, and a copy table holding markup is a defect that will reach the catalogue
      and the walk pages.
- [ ] Reject a paste that carries markup, with a visible message. Do not silently strip it.
- [ ] **Live contract validation, and this is the feature that earns the task.** The rules are
      already executable: R1's three-word `button.` cap, R3's twelve words for `advice.`, R5's no em
      dash, R6's no emoji including U+2600 to U+27BF, R14's Title Case. Run them **as he types** and
      show the failure inline. Today those rules fail at merge, hours later, with no context. Here
      they fail in the sentence that broke them.
- [ ] The patch's `copy` map is `{ key: newValue }`. The applier rewrites `DEFAULT_COPY` entries in
      place and **regenerates the catalogue afterwards**, because `catalogue.json` pins every string
      byte for byte and a copy change without regeneration is a red suite.
- [ ] **Per-skin edits write to the skin's override table, not the default.** The skin tables are
      deliberate: limelight is lower case, board is upper. An edit made while limelight is showing
      belongs in `copy.limelight.ts`.

## Task 3: assets

**Files:** `src/design/`, the `ArtworkPlaceholder` component, `scripts/design-patch.mjs`

- [ ] In design mode, every `ArtworkPlaceholder` accepts a dropped image and renders it in the
      frame at the real size, so placement can be judged rather than imagined.
- [ ] The file is held as a data URI in `localStorage` for the session and emitted in the patch as
      `{ registerRow, filename, dataUri }`.
- [ ] The applier writes it to `public/` under the register row's name and prints the line to add
      to `docs/design/2026-09-04-icon-register.csv`. **It does not edit the register itself** —
      that file is the owner's record of what he has commissioned.
- [ ] Warn on anything over a sensible size. The deployed bundle is 1.3 MB today; a dropped
      screenshot could double it without anyone noticing.

---

## Task 4: layout notes

**Files:** `src/design/`

- [ ] Alt-click, or a mode toggle, pins a note to any element carrying a `data-part` or
      `data-copy-key`.
- [ ] Notes export as `[part-id] text`, the same shape the walk pages already produce, so they drop
      straight into a ledger.
- [ ] **No dragging, no resizing, no absolute positioning.** See the decision above.

## Verification

Everything in `00-CONTEXT.md`, plus, and these are the ones specific to this tool:

- [ ] **The production bundle contains no design-mode marker.** Asserted in CI, not by inspection.
- [ ] A round trip: export a patch, apply it with `--write`, and the app renders what the panel
      showed. This is the whole tool; if it does not hold, nothing else matters.
- [ ] `scripts/design-patch.mjs` without `--write` changes no file. Test it.
- [ ] After a copy patch, `alpha-catalogue --check` and `alpha-walk-pages --check` both pass,
      because the applier regenerated them.
- [ ] Contract validation flags a known-bad string: a four-word `button.`, an em dash, an emoji, a
      lower-case `label.`. Four cases, four failures, in the panel.
- [ ] The skin switcher actually re-renders in the other skin's tokens.

## What this deliberately does not do

- **It does not edit layout.** Stated three times in this document because it is the thing most
  likely to be added later without noticing what it costs.
- **It does not touch the R10 modules.** The long-form content — `bodyEquations.ts`,
  `guidanceReferences.ts`, `sexRationale.ts` and the rest — carries citations and structure, not
  loose strings. Editing those in a WYSIWYG is how a DOI gets mangled.
- **It does not ship.** If it ever appears in a production bundle, the CI grep has failed and that
  is a bug of its own.
